  the live API, because the safety prefix refuses it.
- `opalstack_mailuser` manages `procmailrc` and the four `autoresponder_*` fields, after
  `TestFindingMailFilter`. Each is Optional and Computed and is sent only when the plan changes
  it, so a configuration that names none of them plans nothing: `TestMailUserUpgradeFrom012`
  writes a state with the 0.1.2 schema and checks exactly that. The newline the API drops from
  `procmailrc` is absorbed in two places: the model keeps the text as written when the API's
  differs only in the white space around it, and a plan modifier plans the state when the
  configuration differs from it only in that.
- **All of this is tested offline only.** `TestAccOSVar` and the filter steps of `TestAccMail` are
  written and have not run against the real account yet. `TestAccOSVar` needs the write switch
  of osvar; the sweeper covers the kind.

## Decisions that differ from the first design notes

- **Waiting fails fast only on a `_FAILED` state.** The spec's state enum has no failure value, but
  the live API reports `INSTALL_FAILED` for an app whose installer did not succeed. Otherwise
  `WaitReady` ends on ready, on an error from the read, or on the caller's deadline, and its
  timeout error names the last state seen.
- **Deletion is detected by 404 on `read`**, not by polling the list. `WaitReady` returns the object from the poll that reported ready.
- **A POST is not retried on a server error or a transport error**, only on 429. A repeated
  create could make a second object. A GET is retried on 429, on any 5xx and on a transport error.
  A `Retry-After` header is obeyed up to one minute, and a 429 holds back every other request too.
- **An id that is not a UUID is refused before any request.** The API answers such an id with 404,
  which would read as "deleted".
- **A safety-prefix refusal never matches `ErrNotFound`**, even when the lookup behind it did.
- **The safety prefix costs one extra GET per update and delete**, because those requests carry an
  id and the prefix is a property of the name. When the name cannot be read the write is refused.
- **The safety prefix also checks the new name of a rename**, and refuses any write it cannot tie
  to a name. It reads the request as it will be sent, so a new request type needs no code for it.
- **A wait sleeps before its first poll**, because the POST it follows already said "pending".
- **`dkim_privkey` is never decoded.** The client's domain type has no field for it.
- **`domain` has an update** (`delegated_dns_zone`), which the first notes ruled out.
- **`dnsrecord` update leaves out `domain` and `type`** although the API accepts them.

- **`opalstack_app.json` manages only the keys the configuration names.** The API fills in
  settings of its own (`php_version` on an `APA` app), and those never show as a diff.
- **A type change to or from `CUS` replaces the app.** In place the API changes the type but
  assigns no port.
- **A site's domains and routes are sets**, a site needs `ip4_id` or `ip6_id`, and a route `uri`
  must end with `/`, because the API appends one.
- **Database users and mailboxes take an optional `password`**, changed in place and never read
  back; without one the API's `default_password` is kept, as for a shell user.
- **`opalstack_cert` never waits**: a certificate has no state. Its key lives in the Terraform
  state, and is never read from the API although every read returns it.
- **An address is judged by its `source` for the safety prefix**, through a per-kind name field on
  `ReadKind`, and by the mailboxes it delivers to.
- **`opalstack_osuser` sets no password.** The API chooses one and reports it once, as
  `default_password`.
- **The framework's pointer getters turn an unknown value into a zero.** Requests are built with
  `knownBool`, `knownInt64` and `knownString` from `internal/provider/resource.go` instead.

## The test setup

- A sandbox shell user and a base domain for tests exist on the account. Their names are not in
  this repository; tests take them from `OPALSTACK_TEST_OSUSER`, `OPALSTACK_TEST_OSUSER_ID` and
  `OPALSTACK_TEST_DOMAIN_BASE`. The sandbox user's name deliberately does not start with
  `tfacc-`, so neither the safety prefix nor the sweeper can ever match it.
- The test token (`pass` entry `Opalstack/tokens/tfacc`) is kept **narrow**: service read switches
  only. Opalstack's per-object ACL turned out not to allow creating anything, so a testing session
  turns on the service write switch of each kind it tests, and **while those are on the token can
  change every object of those kinds on the account, and the safety prefix is the only thing
  between a test and a real object**. Every acceptance test configures the provider with
  `safety_prefix`, and the app and site tests with `safety_osuser_id` as well.
- The procedure, start and end of a testing session. The owner keeps a script outside this
  repository that flips the switches in the dashboard (it reads checkbox states only, never the
  dialog's text, which shows the key):
  1. turn write on for the kinds under test;
  2. test;
  3. `make sweep`, which must report 0 leftovers;
  4. turn every write switch off, then confirm with `scripts/probe-token.sh` (lists still answer
     200) and `scripts/probe-write.sh` (the create answers 403).
- The owner's wrapper that exports those variables and the token lives outside this repository.
